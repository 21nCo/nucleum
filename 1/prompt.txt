 My view of the architecture

 The skeleton is good. It's a real acyclic graph, enforced including type-only imports, with no spare permissions. Host inversion through configure-hosts.ts is clean, the composition root has
 an allowlist, and the feature entry-point contract is explicit. The weak spots are around that core:

 1. Runtime is a catch-all. Workflow code has leaked into it:
   - session-cleanup.ts signs out and redirects.
   - network/http-operation.ts reloads the page on a 401.
   - commands/command-kind.ts builds command-palette labels for its only consumer, the command bar.
   - navigation-request.ts hard-codes "custom:navigation", duplicating GlobalEvent.
 2. Runtime and config are matrix owners but not workspaces. They ride on the aggregate @nucleum/client package. Its manifest declares @nucleum/shell and @nucleum/surfaces, which creates a
    package-level cycle, plus unused dependencies such as pdf-lib and @datafn/client.
 3. config is not declarative. It holds a mutable host (product-resources.ts), a 44-member feature enum, and a dead blank.json → blank store chain.
 4. Export maps have drifted, and only the alias map hides it:
   - shared-state/package.json has no ./product/*.
   - datafn/package.json is missing visibility-sync, resource-filters, search-provider and record-id.
   - static/package.json exports assets/ and monaco-editor/, which don't exist.
 5. client/tsconfig.json include lists only retired directories (appearance, commands, events, state, layout, and so on), plus ui, products, extensions and next. Most current owners aren't
    covered. [INFERENCE] A client-level tsc run doesn't check most of the code.
 6. The checker has accumulated cruft:
   - About 6 special-case shared-state rules are covered by the generic one. Each adds only one unique ban: app.store → account.store, or importing app.store.
   - The dead events token at about line 389, and the link.type.ts exclusion at about line 399 that can never match.
   - About 150 of roughly 165 retired-client-paths.json entries are history only.
   - retiredOwnershipPaths entries without an extension can never match.
   - client/{appearance,files,preferences,…} can be recreated as directories without being flagged.

 1. Make the checker resolve $local, $lib and $app. Move product.resolver into composition or routes, since product selection is an app-host concern.
 2. Turn client/runtime and client/config into real workspaces, so matrix owners and workspaces line up. Then add a check that every cross-package import is listed in that package's exports.

Documentation gaps (docs say something the tooling doesn't do)

1. type-ownership.md:51 misstates the schema rule. "It rejects production schema, shared, server, and service imports into client code" — the checker (architecture.mjs:352) bans thereverse direction: schema|shared|services|server importing into client/. Client→schema imports are pervasive (58 files across datafn, runtime, shared-state, features, surfaces, shell,products) and completely legal. The sentence reads as a client→schema ban that doesn't exist.
2. The client→schema/shared relationship is entirely undocumented. Schema isn't a matrix owner, so those imports are governed only by manifest declarations, not direction. The map doccalls its table "the full direct-import list" — it isn't, without a schema/shared column or a "universal leaf dependency" note.
3. client-boundaries.md's Ownership table omits real owners: extensions, ambient, next, theme, static (all matrix owners), and the surfaces enumeration omits sharing (which exists andis named in the 1.10 sync report).

Leftovers (repo side)

• dev:gathery and dev:memotron-clipper are dead scripts — turbo dry-run: "No package found with name 'gathery-app'/'memotron-clipper'". Meanwhile client/products/gathery is git-tracked,modified source with no Product.GATHERY enum entry, no app workspace, and zero mention in AGENTS/docs. It's a half-wired product that needs a decision.
• tests workspace is still named tidigit-tests, and test filters it by that name — a Tidigit→Nucleum rename leftover (also tidigit.com/tidigit.dev in fixtures).
• check:no-legacy-runtime is orphaned — defined in root package.json but not in lint, test, or either CI workflow.
• apps/fetch-json-data.js — loose script file sitting at the apps root.

Thoughts on the architecture

The enforcement-first design is genuinely strong — "checker wins over docs," ledger-driven retirement, both-direction feature-entry contracts, and transitive checks for the twoload-bearing invariants (portable UI purity, shared-state never reaching composition). Most monorepos don't have this. Two structural concerns:

1. Special-case accumulation in architecture.mjs. Per-file regex bans (record-renderer.ts, focus/composition.utils.ts, shortcuts/*, resource-action-host.ts, the retiredStoreMethods map)encode history as code. They're effective but invisible to the docs, and they exist because the matrix can't express intra-owner or sub-owner rules. Moving them into a ledger file(like retired-client-paths.json / the type inventory) keeps the checker generic and the rules auditable in one place.
2. Schema is a silent universal dependency. Every layer may import it, untracked by the matrix. It works today, but the dependency story the docs tell ("this is the full direct-importlist") has a hole exactly where drift is most likely.
