# Contributor and maintainer orientation

As noted in README.md, external contributions are not currently accepted. This guide documents the workflow for maintainers and authorized agents.

Start with [AGENTS.md](AGENTS.md), [system architecture](docs/architecture/system-architecture.md), [client boundaries](docs/architecture/client-boundaries.md), and [type ownership](docs/architecture/type-ownership.md).

Confirm the active product in `client/products` and `client/config`. Reuse `@21n/ui/elements` for atomic controls, `@21n/ui/compositions` for portable domain-neutral compound UI, `@21n/ui/actions` for generic DOM behavior, `@21n/ui/icons` for portable icons, `@21n/ui/illustrations` for artwork, and `@21n/ui/branding` for pure visual brand assets. UI-wide platform state and dependency-inversion contracts belong to `@21n/ui/environment` and `@21n/ui/hosts`, not under an individual element. Keep a composition shared when credible future reuse is intentional even if it currently has one consumer. The entire UI package must remain independent of application state, runtime, shell, products, features, DataFn, persistence, schema, and domain state; inject product behavior through props or narrow host contracts. Keep product-aware branding and other connected adapters with application composition. The concrete application shell lives under `client/shell`; the generic `client/layout`, `client/branding`, `client/illustrations`, `client/icons`, `client/iconsV2`, `client/commands`, `client/events`, and `client/state` owners are retired. Product-independent app-context, appearance, command, event, file, notification, preference, resource, and shortcut behavior belongs to named `@nucleum/shared-state/*` subpaths, which must not depend on application composition, shell, surfaces, features, or product implementations. Connected notification rendering and shortcut execution belong to the shell, while shortcut settings UI belongs under `client/surfaces/settings/shortcuts`.

Use repository scripts for setup, compilation, tests, and builds. Run architecture and type-ownership checks for moves, and include a forward migration when generated database mappings change. Do not modify existing tests without the per-file authorization required by AGENTS.md.

PRs should describe the user-visible result, ownership changes, checks performed, and limitations. Do not include secrets, local environment files, build output, or unrelated workspace changes.
